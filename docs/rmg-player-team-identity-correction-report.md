# RMG player and team identity correction

Completed implementation child, 2026-09-05. Implements requirement 3 of `rmg-audit-corrections-requirements.md` under `bugfix-rmg-player-team-identity-20260905`. Source chain: `project.md` → Phase 6 correction parent/child in `PLAN.md` and `ops/progress.json` → requirements/source audit → runtime owners → evidence below. This child does not establish full native parity or complete the correction goal.

## Confirmed owner and defect

The recovered `FinalHeaderWriteoutResult4ac857` already contains active color slots, `team_count`, and `player_team_assignments`. `0x4acde8..0x4ad140` writes zero teams for effective free-for-all, otherwise the final eight color-indexed team assignments. Runtime projection discarded these team fields. `map_package_service.cpp` exported faction strings, while the session bridge expected enemy dictionaries. The fallback in `EnemyTurnRules` then grouped towns, treasury, commander state and turns by faction. The audited six/eight-player cases retained only four opponents.

## Implementation contract

- Stable `player_id = player_<one-based source color slot>` identifies each generated controller. `faction_id` remains a real immutable original-content id, never a synthetic player alias.
- Source-assigned teams are copied from the owned final header into projection and package records. A zero source team count means each player has its own team. No new RNG draw, faction-based team inference, topology, object placement or native generation rule.
- Session `players` and `active_player_id`, town `controlling_player_id`, enemy state `player_id`, and raid `spawned_by_player_id` are explicit persistent ownership fields. Separate controllers may use the same faction and hero template without sharing commander instances, treasury, tasks or memory.
- `PlayerIdentityRules.gd` resolves controllers separately from faction content and team relations. EnemyTurn/EnemyAdventure ownership, economy, town/raid lists, tasks, scouting memory, commander reconciliation and spawn identities use the actual player. Content selection, strategy, artifact affinity and public faction labels still resolve original faction content.
- Town capture, occupation/fronts, resource/artifact claims, stationed defenders, battle context and aftermath preserve the actual controller. Same-faction town transfers change ownership without changing the founding `owner_slot`. Mine retake mutation facts retain the former player, not the shared faction. Mine labels show the faction and player number rather than raw internal ids.
- Team checks prevent allied resource contention and allied-human attack targeting/interception. This does not add AI-versus-AI combat rules, shared vision, diplomacy, hotseat or multiplayer. Human-owned resource APIs retain their existing `player` alias, resolved to `active_player_id` for team comparisons. The supported generated runtime is one human plus computer players; multi-human play remains outside this correction's certified boundary.

## Save compatibility

New sessions use additive `player_identity_version: 1`, `player_identity_mode: native_player_slots_v1`, with persistent player/team/controller fields; the outer save schema is unchanged. Older native packages still contain source slots and can start separate-player games, but missing source team metadata means free-for-all rather than an inferred faction alliance.

Already-played generated saves without player records explicitly retain `player_identity_version: 0`, `player_identity_mode: legacy_generated_faction_v0`. Their historical pooled treasury, captures and commander progress cannot be decomposed from initial slots without inventing ownership or duplicating resources. They continue with their original faction-keyed interpretation. The validation invokes the actual pre-correction bridge from `df93e008ff8436811e58356107df71c3634be123`, preserves four pooled states with 12,345 gold each, and verifies production disk restoration and deterministic continuation. Authored scenarios likewise keep legacy faction-keyed behavior.
