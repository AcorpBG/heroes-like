# Native RMG Core Drift Against H3MapEd Recovery Ledger

Document role: focused drift audit for `src/gdextension/src/rmg_native_core.cpp` and `src/gdextension/include/rmg_native_core.hpp` against `docs/h3maped-rmg-end-to-end-behavior.md`.

This is an audit/marking document only. It does not claim implementation progress. It deliberately compares the active `rmg_native_core` adapter surface to the recovered H3MapEd end-to-end behavior, not to final-map counts, package reports, or prior proxy code.

## Verdict

`rmg_native_core` is not a native port of the recovered H3MapEd RMG chain. It is a no-Godot blocked wrapper around a partial support path:

- controlled-case parsing;
- optional setup/template catalog feed;
- coordinate/source-node/boundary/span-fill/TerrainPlacement support call into `h3maped_rmg_core`;
- a partial object source-record catalog mirror with corrected metadata `+0x08` wrapper-bucket lanes;
- blocked JSON emission.

That is useful as a fail-closed diagnostic wrapper, but it drifts from the recovery ledger anywhere a caller treats it as an entrypoint-to-writeout native generator.

Current audit pass: 2026-06-19. The pass compares the active `src/gdextension/src/rmg_native_core.cpp`, `src/gdextension/include/rmg_native_core.hpp`, and the shared `h3maped_rmg_core` surfaces they call against `docs/h3maped-rmg-end-to-end-behavior.md`. One important source-backed correction is included from the recovered object metadata artifact because the ledger only names the wrapper/selector functions at a high level: H3MapEd routes loaded object wrappers by object metadata entry `+0x08` bucket index, not by copied source-record type `+0x1c`.

## Short Form

The native wrapper currently reaches only this subset:

`controlled case -> optional 0x49ecf2 -> optional recovered catalog 0x4ac552 helper with accepted candidate-container records and source-owner/player-slot buffers -> 0x4a218c/0x4a1f3b/0x4a19ed -> 0x4a3a03/0x4cca55 -> 0x4a2777/0x4a325d/0x4a3710 -> 0x49b53d/0x4a3f27/TerrainPlacement support -> partial object catalog mirror with metadata +0x08 wrapper buckets -> blocked JSON`.

It does not own:

- H3MapEd UI/entrypoint/private generator object setup;
- generator object vectors beyond the recovered accepted candidate containers and player/source-owner slot buffers;
- complete candidate/source setup containers;
- full raw copied source records carried through wrapper selection, descriptor joins, object selection, and materialization;
- fully mutated stride-`0x30` generated-cell records beyond the reset/owner/terrain partial record carrier;
- relation/scoring/object caller order;
- town/castle placement;
- reward/guard projection and attachment;
- endpoint/cursor/connection fallback materialization;
- road/river overlay writeback;
- final tile/object/header stream writeout;
- same-run private-state comparison.

Source-handler pending entries are not on the current direct one-level land supported path per the recovery ledger's source-backed exclusion. That absence should remain explicitly excluded, not reintroduced through guessed handler logic.
